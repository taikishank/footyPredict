# Training Methodology & Model Architecture for v4

## Current project state (from code inspection, not external research)

This section is not sourced externally — it is a direct read of the project's own code, included because the report writer needs it as the baseline the external findings are compared against.

- **Optimizer**: `ml/goals_lib.py` fits Dixon-Coles attack/defence/home-advantage/rho parameters via `scipy.optimize.minimize(..., jac=True, method="L-BFGS-B", bounds=bounds)` — i.e., quasi-Newton (L-BFGS-B) with an analytic gradient supplied (`jac=True`), not finite-difference, and with box bounds on log-scale parameters (`PARAM_CAP = 1.5`, `RHO_MIN/MAX`). This is already the standard, well-evidenced choice (see Key Question 1 below) — the project is not leaving obvious optimizer gains on the table.
- **Regularization**: a *fixed-precision* L2/ridge-style Gaussian prior (`RIDGE = 5.0`) pulls every club's attack/defence parameter toward the league mean, deliberately *not* scaled by each club's own sample size (comment: "a constant prior shrinks a four-match club hard and a full-season club barely... deliberately intended"). This is a hand-tuned empirical-Bayes-*like* shrinkage but with a fixed hyperparameter rather than one estimated from the data's own between-club variance (i.e., not full empirical Bayes / hierarchical Bayes — see Key Question 2).
- **Time weighting**: matches are weighted in the *likelihood itself* by `0.5 ** (t / HALF_LIFE)` (exponential/half-life decay), swept as a hyperparameter, and refit on a cadence (also swept) as the archive advances — this is literally "the other half of Dixon and Coles' (1997) paper" per the code's own docstring, and per the commit `a41eb4b`, solving for it via batch MLE beat the project's earlier online-gradient-step approximation (`ratings_lib.AttackDefence`) by +0.00341 log loss [+0.00227, +0.00457], described as "the largest gain since the ratings phase."
- **Validation scheme**: `ml/tune.py` and `ml/rating_ablate.py` already support two protocols — `split` (a single chronological holdout, the project's original/default) and `rolling` (5-fold expanding-window / rolling-origin), with `rolling` treated as authoritative and `split` retained only as a cheap control. This is walk-forward-aware, not a naive random split.
- **Ensembling/hybrid modeling already tried**: the same commit found that "pooling the score model [Dixon-Coles] with v3 [gradient-boosted tree model] in log space" (i.e., averaging/stacking the two models' predicted probabilities in log-odds space) is worth +0.00341 log loss — the single largest recent gain — while handing the GBT the raw Dixon-Coles matrix probabilities as input features, or the two full forecaster outputs as columns, bought only about a third as much. This means: **a Dixon-Coles + GBT hybrid is already implemented and is the current best result**, and the project's own evidence says post-hoc log-space pooling of two independently-fit models beats feeding one model's output as a feature into the other.
- **Leakage/skew auditing already underway**: commit `225f9bd` ("Measure the train/serve skew in the form window, and price the refusals") indicates the project already audits train/serve skew for at least one feature family, and `1f516d3` ("Reconstruct v2 edges for kicked-off fixtures, with the leak check enforced") indicates an explicit automated leak check exists in the backtest pipeline.

This baseline matters for interpreting the external research below: several "textbook" recommendations (L-BFGS for MLE, time-decay in the likelihood, walk-forward CV, statistical+ML stacking) are **already implemented**. The genuinely open gaps are: (a) fixed vs. data-driven/hierarchical shrinkage, (b) whether the walk-forward scheme has a leakage-relevant weak point specific to how team-strength parameters are refit relative to the match being predicted, and (c) whether bagging/multiple-seed ensembling of the MLE fit itself (as opposed to model-family stacking, already tried) has been evaluated.

## What optimization method is currently used to fit the model? Is training walk-forward/time-series aware, or is there risk of look-ahead bias?

### Takeaway
The project already uses the field-standard approach for Dixon-Coles fitting — L-BFGS-B quasi-Newton MLE with an analytic gradient, exponential time-decay weighting in the likelihood, and expanding-window (rolling-origin) walk-forward validation as its primary protocol — so there is little external evidence that switching optimizers or adopting basic walk-forward CV would move log loss further; the more promising unaudited risk is *leakage within the walk-forward refit boundary itself* (label-window overlap / embargo), a pattern well documented in adjacent time-series ML literature but not yet cross-checked against this project's specific refit cadence.

### Cited Findings
- Public Dixon-Coles implementations converge to the same practice this project uses: "parameters are estimated by maximizing the time-weighted log-likelihood using L-BFGS-B (a quasi-Newton method that handles bound constraints well)," converging in ~100 iterations / 3-5 seconds for an EPL-scale dataset — [dashee87.github.io, Predicting Football Results With Statistical Modelling: Dixon-Coles and Time-Weighting](https://dashee87.github.io/football/python/predicting-football-results-with-statistical-modelling-dixon-coles-and-time-weighting/)
- A separate independent Dixon-Coles implementation writeup describes a further optimizer-level speedup: encoding the model's sum-to-zero identifiability constraint directly into the design matrix (rather than via Lagrange-multiplier constrained optimization) cuts fitting time from ~40s to ~6-7s using plain BFGS — a genuine but purely computational-efficiency gain, not a log-loss gain — [opisthokonta.net, "The Dixon-Coles model, part 4: A trick to speed up estimation"](https://opisthokonta.net/?p=939)
- Dixon and Coles' original time-weighting scheme uses φ(t) = exp(-ξt) with a fitted decay parameter (ξ ≈ 0.0065 in half-weeks in the original 1997 paper), and practitioners note "you need to find the decay rate to your own dataset and not assume [the original paper's value] is optimal today" — [dashee87.github.io](https://dashee87.github.io/football/python/predicting-football-results-with-statistical-modelling-dixon-coles-and-time-weighting/)
- In time-series/financial ML, "standard k-fold cross-validation silently leaks data" because labels built from forward-looking windows let a training observation share outcome information with a temporally-separated test observation; López de Prado's fix is **purging** (removing training observations whose label window overlaps the test window) plus an **embargo** (excluding a further buffer of training observations immediately after the test set, to neutralize residual serial correlation) — [Purged cross-validation, Wikipedia](https://en.wikipedia.org/wiki/Purged_cross-validation); [Quant Memo, "Purged & Embargoed Cross-Validation, Explained"](https://quantmemo.com/concepts/purged-embargoed-cv)
- Walk-forward validation with an expanding window is described generally as "the k-fold cross validation of the time series world," ensuring "future data is never used to predict past values," with expanding windows favoring stability when structural breaks are rare and sliding/rolling windows preferred when older data may be stale — [MachineLearningMastery, "5 Ways to Use Cross-Validation to Improve Time Series Models"](https://machinelearningmastery.com/5-ways-to-use-cross-validation-to-improve-time-series-models/); [Medium/eatpredlove, "Time Series Cross-validation — a walk forward approach"](https://medium.com/eatpredlove/time-series-cross-validation-a-walk-forward-approach-in-python-8534dd1db51a)
- Combinatorial Purged Cross-Validation (CPCV) generates multiple train/test path combinations specifically to address the fact that a single walk-forward path only tests one particular ordering of luck/regime — [Quant Memo](https://quantmemo.com/concepts/purged-embargoed-cv); [Scribd summary of SSRN CPCV paper](https://www.scribd.com/document/725401650/SSRN-id4778909)

### Inferences
- Because this project already uses L-BFGS-B with an analytic gradient and already sweeps the time-decay half-life and refit cadence as documented in `ml/goals_lib.py` and validated by commit `a41eb4b`'s ablation gate, there is essentially no evidence base suggesting further optimizer-family changes (e.g. Newton-Raphson with an exact Hessian) would move log loss meaningfully — L-BFGS-B's quasi-Newton Hessian approximation is standard practice in the reference implementations found, and the marginal accuracy of an exact Hessian on a well-behaved, low-dimensional (per-club attack/defence) MLE problem is not something the literature searched here claims matters for solution quality, only possibly for iteration count.
- The one concrete, underexplored risk given the project's walk-forward setup: purging/embargo is a check specific to whether a training fixture's *own outcome label* leaks into a nearby test fixture through a shared feature-construction window (e.g., if opponent-adjusted ratings for match X on date D are built using a window that already includes match Y, and match Y is in a "future" validation fold relative to some other split point). The project's `rolling` protocol is expanding-window by fixture date, which handles the coarse ordering, but nothing in the skimmed code demonstrates an explicit *embargo buffer* around each fold boundary — worth an explicit audit given the project already found and fixed a train/serve skew and a leak in the v2 edge reconstruction (commits `225f9bd`, `1f516d3`).

### Gaps
- Could not verify from external sources whether Dixon-Coles-specific literature has ever formally applied purging/embargo (this is a finance-ML concept); no football-prediction paper surfaced in search explicitly discusses embargo periods for match-level walk-forward folds. This is an inference/transfer from an adjacent field, not a confirmed football-specific finding — flag as moderate-confidence.
- Did not obtain full-text access to the two most relevant academic PDFs (arXiv 2403.07669, UCL/Baio-Blangiardo hierarchical model) — WebFetch returned corrupted binary content for both. Findings on those papers below rely on abstract-level text and secondary summaries only.

## What well-evidenced training-methodology improvements has this project likely NOT tried?

### Takeaway
The clearest evidence-backed gap is **hierarchical/empirical-Bayes shrinkage with a data-estimated (rather than fixed) precision**, since the literature explicitly frames this as superior to a fixed ridge constant; ensembling via bootstrap/multi-seed averaging of the MLE fit itself is well-established in general ML but has no football-specific evidence found and is a lower-confidence bet than the shrinkage change, which the project's own comments already gesture toward but declined to implement.

### Cited Findings
- Baio and Blangiardo (2010) introduced hierarchical shrinkage of club attack/defence parameters in a Bayesian football model, treating each club's parameters as drawn from a shared population-level (hyperprior) distribution rather than fit independently or shrunk toward a fixed point with a fixed strength — [ResearchGate listing, "Bayesian hierarchical model for the prediction of football results"](https://www.researchgate.net/publication/46527004_Bayesian_hierarchical_model_for_the_prediction_of_football_results)
- In empirical Bayes estimation generally, "the estimate is shrunken towards the mean of the prior distribution, and the amount of shrinkage decreases as more evidence is gathered" — i.e., the shrinkage *strength* is itself estimated from the population's observed variance, not fixed a priori — [arXiv 1807.09236, "Improving pairwise comparison models using Empirical Bayes shrinkage"](https://arxiv.org/pdf/1807.09236)
- A known failure mode of hierarchical/shrinkage models is **overshrinkage**: "more extreme values get pulled back towards the overall average... causing parameter estimates to get regressed towards the mean" beyond what is warranted — a genuine risk when applying pooling too aggressively — [search synthesis citing hierarchical modeling literature, no single primary source retrieved in full text; treat as a well-known but not individually pinned-down caveat]
- Gradient-boosted tree ensembling and stacking are dominant in general ML competitions: "ensemble algorithms involving boosted machine learning models tend to win many Kaggle competitions," and "stacked ensembles shine... where every decimal point matters," typically via cross-validated out-of-fold predictions fed to a meta-learner (e.g., ridge regression) specifically to "mitigate risks of overfitting and data leakage" — [ml4devs.com, "Ensemble Learning: Bagging, Boosting, And Stacking Explained"](https://www.ml4devs.com/what-is/ensemble-learning-bagging-boosting-stacking/); [Nature Scientific Reports, stacked GB-XGBoost-ridge ensemble example](https://www.nature.com/articles/s41598-026-47042-3)
- Bagging (bootstrap aggregation) "reduces the variance component of the overall generalization error" by training multiple models independently on bootstrap resamples and averaging — a generic, well-evidenced technique, but no football- or Dixon-Coles-specific application of bagging the MLE fit (e.g., across bootstrap-resampled seasons or random restarts) was found in this search — [QuantStart, "Bootstrap Aggregation, Random Forests and Boosted Trees"](https://www.quantstart.com/articles/bootstrap-aggregation-random-forests-and-boosted-trees/)
- On combined loss objectives: "the Expected Calibration Error (ECE) metric could also be added as a component to the loss function to create a multi-objective loss function covering both model accuracy and calibration error," though log-score/NLL remains "one of the simplest and most widely used scoring rules" and is itself already a strictly proper (calibration-rewarding) rule — [emergentmind.com, "Probabilistic Loss Functions"](https://www.emergentmind.com/topics/probabilistic-loss-functions); [MetricGate, "Brier Score vs Log Loss vs Calibration"](https://metricgate.com/blogs/brier-score-vs-log-loss-vs-calibration/)

### Inferences
- The project's own `RIDGE = 5.0` constant, with the code comment explicitly reasoning about why it is deliberately *not* scaled per-club, is precisely the design point that empirical/hierarchical Bayes literature argues against: a *fixed* precision is a special case of hierarchical shrinkage where the population variance hyperparameter has been hand-set rather than estimated jointly with the club parameters. Given the project's demonstrated rigor (pre-registered ablation gates, placebo checks), a natural next ablation is: refit with the shrinkage precision itself estimated via a second level (empirical Bayes: estimate the between-club variance of attack/defence params from the data, then use its inverse as the ridge precision) or a full hierarchical prior (hyperpriors on the population mean/variance, fit either by an EM-style empirical Bayes step or by treating it as an additional MLE parameter). This is a natural, low-risk-to-implement extension of code the project already has (same `minimize` call, one or two extra parameters or an outer EM loop), which fits this project's preference for ablating rather than assuming.
- Since the project already tried and validated one ensembling axis (Dixon-Coles × GBT pooled in log space, +0.00341), the *un-tried* ensembling axis specifically flagged as well-evidenced elsewhere is **within-model-family ensembling**: bagging the Dixon-Coles MLE fit itself (e.g., multiple fits over bootstrap-resampled match sets, or multiple random restarts/seeds if any part of the optimization has stochastic initialization) and averaging the resulting rate/probability predictions, which is a distinct mechanism from cross-family stacking and targets *fit variance* (small-sample noise in per-club parameters) rather than *shape misspecification* (which the project's fit-vs-shape finding already ruled out as the bigger lever). Given the recent finding that "the gain is in the fit, not the shape," reducing fit variance via bagging is a plausible next place to look, though no football-specific evidence for this exact combination was found — moderate confidence, worth a cheap ablation rather than a strong prior.
- The combined-loss-with-calibration idea is weakly evidenced for this project's case: since log loss is already a strictly proper scoring rule that penalizes poor calibration, and the project already computes ratios against the closing line (a strong external calibration reference), an explicit calibration-error term added to the training objective is more likely to help *only* if the current MLE, under model misspecification, produces systematically over/under-confident probabilities that log loss alone under-penalizes at the tails — a real but narrower failure mode than the general framing suggests.

### Gaps
- Could not find any paper directly combining Dixon-Coles-style statistical models with formal hierarchical/empirical Bayes shrinkage *and* reporting a quantified log-loss or accuracy improvement over fixed-ridge shrinkage — the Baio-Blangiardo paper's specific numerical results were not retrievable (PDF fetch failed on both attempts), so the *magnitude* of benefit from hierarchical over fixed-ridge shrinkage is asserted qualitatively by secondary sources but not confirmed with a number here.
- No football-specific citation found for bagging/bootstrap-ensembling a Dixon-Coles MLE fit across random seeds or resamples — this is an inference from general ML ensembling literature, not a directly evidenced football-prediction finding. Flag as a plausible-but-unconfirmed technique.
- Did not find literature specifically on multilevel pooling *across leagues/seasons* (as opposed to across clubs within one league) for Dixon-Coles-style models, which was one of the explicitly asked-about mechanisms; this remains an open gap.

## What does the statistical-vs-ML literature say about when ML models beat/lose to well-fit statistical models, and does that suggest a hybrid (GBT-on-residuals) is worth trying?

### Takeaway
The literature broadly finds that gradient-boosted trees can match or exceed Dixon-Coles-style models but typically only when paired with strong domain-specific rating features (Elo/pi-ratings) rather than raw data, and one review explicitly states Dixon-Coles "has not been significantly improved using machine learning techniques" on its own — which is consistent with this project's own finding that the win came from *pooling* forecaster outputs in log-odds space, not from feeding the tree richer raw inputs, so a residual-on-GBT hybrid is worth trying only in the log-space-pooling form already validated, not as a from-scratch redesign.

### Cited Findings
- A review summary states: "Random Forests combined with Poisson-based team ratings have been shown to outperform standard statistical models. XGBoost has been reported to surpass both deep learning and traditional ML approaches across multiple leagues. However, Dixon & Coles is still seen as one of the leading examples of statistical modelling for football and has not been significantly improved using machine learning techniques [on its own]" — [thexgfootballclub.substack.com, "Which Machine Learning Models Perform Best for Football Match Prediction?"](https://thexgfootballclub.substack.com/p/which-machine-learning-models-perform)
- A 2024 review chapter states plainly: "gradient-boosted tree models such as CatBoost, applied to soccer-specific ratings such as pi-ratings, are currently the best-performing models on datasets containing only goals as the match features," while also noting a lack of "thorough comparison of the performance of deep learning models and Random Forest on a range of datasets with different types of features" — i.e., the field's own comparisons are acknowledged as incomplete — [arXiv 2403.07669 abstract, "Machine Learning for Soccer Match Result Prediction"](https://arxiv.org/abs/2403.07669)
- Constantinou, Fenton and Neil's pi-rating system was shown to outperform an Elo adaptation, and "ensemble methods, particularly gradient-boosted trees (e.g., XGBoost, CatBoost), excel when paired with tailored features like Elo, pi-, or Berrar ratings" — reinforcing that ML's edge in this domain comes from good input ratings/features, not from the tree architecture alone — [search synthesis of Constantinou/Fenton literature](https://www.sciencedirect.com/science/article/abs/pii/S0169207009001708)
- Constantinou (2019) built a hybrid combining a dynamic pi-rating-based rating system with a Bayesian Network — an explicit statistical-model + probabilistic-graphical-model hybrid in the published literature, a structurally different hybrid than GBT-on-residuals but evidence that hybridizing a rating system with a second probabilistic layer is an established pattern in this specific research area — [search synthesis](https://www.sciencedirect.com/science/article/abs/pii/S0169207018300116)
- General stacking literature: "cross-validation is typically employed to produce the base-level outputs in stacking, thereby mitigating risks of overfitting and data leakage" when combining a boosting model and another model with a meta-learner — [Nature Scientific Reports stacking example](https://www.nature.com/articles/s41598-026-47042-3)

### Inferences
- The project's own result — pooling Dixon-Coles and the GBT model (v3) in log space beats handing the GBT the Dixon-Coles matrix as a feature — is directly consistent with the literature's framing that ML's advantage in this domain comes from strong *inputs*, not from architectural flexibility to discover the Dixon-Coles-like structure on its own; feeding a tree the raw score-matrix probabilities apparently gives it a redundant, hard-to-use feature rather than new information, whereas independently fitting each model and combining post-hoc(in log-odds space, equivalent to a weighted geometric mean of probabilities) let each model contribute its own well-calibrated but different information. This suggests future hybrid attempts should keep the same **late-fusion, log-space pooling** structure (potentially with a learned or per-market-segment weight, i.e. a simple logistic/meta-learner on the two log-odds columns, since the "same two forecasters as columns" version already recovered a third of the benefit — a full stacking meta-learner one level up from that, rather than a bigger tree, might close more of the remaining gap) rather than switching to an early-fusion "GBT on Dixon-Coles residuals in goal-rate space" design that this literature does not clearly support outperforming late fusion.
- No source found directly validates or invalidates "GBT trained on the residuals of Dixon-Coles' expected goals" as a distinct architecture from what the project already tried; the closest analog (feeding the tree the Dixon-Coles probabilities as columns) was already tested and underperformed full log-space pooling, which is at least suggestive evidence against investing further in a residual-based early-fusion redesign, though not a direct test of the residual formulation specifically.

### Gaps
- No literature found that isolates whether ML beats statistical models specifically on **the draw outcome** (the project's remaining hypothesis space per commit `a41eb4b`'s framing that "the draw is not one end of a strength axis"). This is a specific, narrow empirical question the general statistical-vs-ML literature reviewed here does not address.
- Could not obtain full-text of the two most authoritative-looking academic sources (Baio-Blangiardo, arXiv 2403.07669) due to PDF fetch failures, so quantitative log-loss deltas between statistical and ML approaches from primary sources are not available here — only qualitative claims and secondary summaries.

## What common overfitting/leakage pitfalls in football-prediction backtesting should this project audit, given it already found a train/serve skew?

### Takeaway
The general time-series-ML literature (not football-specific, since no football-specific leakage-audit paper was found) converges on three concrete checks — purge/embargo around fold boundaries, ensuring team-strength parameters used to predict a match never include information from that match or its immediate future, and validating against a true out-of-sample future season rather than only cross-validated historical folds — all of which map onto risks this project's `rolling`/`split` protocol does not obviously rule out by construction, and are worth an explicit audit given the project already caught one train/serve skew and one live leak.

### Cited Findings
- The core leakage mechanism in time-series ML: "financial labels are built from forward-looking windows, so an observation in the training set can share outcome information with an observation in the test set even when the two are separated in time" — the fix is purging (remove training observations whose label-construction window overlaps the test period) and embargoing (exclude a buffer immediately after the test set from training) — [Wikipedia, "Purged cross-validation"](https://en.wikipedia.org/wiki/Purged_cross-validation); [Quant Memo](https://quantmemo.com/concepts/purged-embargoed-cv)
- Walk-forward validation is described as necessary specifically because "future data is never used to predict past values," implying the inverse risk — past-data leakage into a model that will be *served* on live data — is the thing a backtest must replicate faithfully, including refit cadence and information cutoffs, or the backtest overstates real performance — [MachineLearningMastery, "How To Backtest Machine Learning Models for Time Series Forecasting"](https://machinelearningmastery.com/backtest-machine-learning-models-time-series-forecasting/)
- Combinatorial Purged Cross-Validation was developed because a single walk-forward path "tests only one particular ordering," and multiple overlapping train/test path combinations with purging give a more robust overfitting estimate than one expanding-window pass — relevant to whether the project's 5-fold rolling protocol could understate variance in the estimated log-loss improvement of any one ablation — [Quant Memo](https://quantmemo.com/concepts/purged-embargoed-cv)

### Inferences
- Given the project's own recent history — a train/serve skew found in the form-window feature (commit `225f9bd`) and a leak that had to be closed and enforced via an explicit check for kicked-off fixtures (commit `1f516d3`) — the most directly applicable general-ML pitfall is **using data from at or after the prediction time to construct the team-strength parameters used for that same prediction** (i.e., the Dixon-Coles fit's "as-of" cutoff must strictly precede the fixture being scored, for every fixture in every fold, not just at the top-level train/test boundary). Since `ml/goals_lib.py`'s docstring says the model is "refitted as the archive advances," the audit-worthy question is whether the refit cadence combined with the rolling-origin fold boundaries could let a fold's *training* refit incorporate matches that are technically after some *validation* matches within the same fold's date range (a purging-style overlap), rather than only checking the coarse train-before-test ordering.
- The literature's "test on a genuinely future season, not just a cross-validated historical fold" principle is one this project's `split` protocol (chronological holdout) already partially embodies as a "control," but the project's own documentation notes `rolling`'s 5 expanding-window folds are treated as decisive over `split` — worth explicitly confirming the last/most-recent rolling fold's validation period is disjoint from and posterior to anything used in tuning hyperparameters (half-life, refit cadence, ridge precision), to avoid the classic pitfall of hyperparameter-tuning-on-the-same-folds-used-to-report-the-result.

### Gaps
- No football-prediction-specific paper was found describing an explicit purge/embargo protocol for match-level walk-forward backtests; this entire section is a transfer of general time-series-ML risk patterns to football and should be flagged to the report writer as inference-level, not a directly cited football-domain finding.
- Could not determine from external research (this was out of scope for web search and would require re-reading `ml/rating_ablate.py`'s `folds()` implementation in detail) whether the project's rolling-origin folds already include an embargo/purge buffer or not — this is a code-level question the report writer or a follow-up code-focused pass should resolve directly rather than treat as an external-literature gap.
